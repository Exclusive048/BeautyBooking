## 1. Находки

### 🔴 F1 — Студийный мастер не видит свои записи в своём кабинете
- **Роут/персона:** `/cabinet/master/{dashboard,bookings,schedule}` · `+79000000200` (Виктория Петрова, Аура).
- **Шаги:** логин → «Записи» → «Расписание».
- **Ожидалось:** её CONFIRMED-запись `seed-aura-qa-confirmed` (26.07, 11:00 МСК) видна; можно подтвердить/отклонить/перенести.
- **Фактически:** kanban «Всего: 0», расписание «20–26 июля · **0 записей**» — при живой брони внутри недели. Контроль: у Марины (Vision) **12** броней — все с `masterProviderId=она`, `providerId=студия`; её кабинет так же пуст.
- **Механизм (код):** все три сервиса фильтруют `providerId = собственный provider мастера` (`src/lib/master/bookings.service.ts:176,206`, `dashboard.service.ts`, `schedule.service.ts:240+`, резолвер `access.ts:getCurrentMasterProviderId`), а студийные брони держат `providerId = провайдер СТУДИИ` + `masterProviderId = мастер`. Ни одна студийная бронь не может пройти фильтр.
- **Следствие:** S5-действия (confirm/decline/reschedule от лица мастера) **недостижимы** — блокированы этой находкой.
- **Консоль/сервер:** чисто (это не ошибка, а неверный фильтр).

### 🔴 F2 — «Перерывы мастеров»: форма игнорирует ввод, пишет дефолт
- **Роут/персона:** `/cabinet/studio/calendar` → «Перерывы» · Виктория (Vision).
- **Шаги:** выбрать Марину, задать 24.07 14:00–15:00, подпись «QA-перерыв» → «Добавить». Дважды, второй раз полностью нативными действиями Playwright (select/fill).
- **Ожидалось:** TimeBlock BREAK для Марины 24.07 14:00–15:00 (салонное).
- **Фактически (DB, оба раза):** `Дарья Морозова · 2026-07-23T08:00Z–09:00Z (=сегодня 13:00–14:00 Ekb) · note=null` — **все четыре поля проигнорированы**, записан дефолт формы.
- **Механизм (код):** `manage-breaks-dialog.tsx:43-59` — reset-эффект зависит от `availableMasters`, который пересоздаётся `masters.filter(...)` **на каждом рендере** → новая identity → эффект сбрасывает state формы после каждого изменения. Любой ввод немедленно затирается дефолтами; submit всегда шлёт их.
- **Что при этом корректно:** оба поля подписаны «· время салона», конверсия дефолта салон→UTC точна (13:00 Ekb → 08:00Z ✓); список «Перерывы дня» рендерит в salon-tz ✓; удаление перерыва работает.
- **Следствие:** админ «ставит обед Марине на завтра», система молча блокирует **Дарье сегодняшний час** — двойная порча данных.

### 🟠 F3 — Отмена записи: «Причина (необязательно)», но API требует её + английская ошибка
- **Роут/персона:** журнал `/cabinet/studio/bookings` → Действия → «Отменить запись» · Виктория.
- **Шаги:** оставить причину пустой → подтвердить.
- **Ожидалось:** отмена (поле помечено «необязательно»).
- **Фактически:** `POST /api/bookings/{id}/cancel` → **400 `VALIDATION_ERROR` «Comment is required»**; в диалоге alert с этим **английским** текстом. С заполненной причиной отмена проходит (статус REJECTED), освобождённое окно **немедленно возвращается** в выдачу (12 → 17 слотов, 15:00 снова доступен ✓).

## 5. Что НЕ файлится (перепроверено, артефакты)

- «Мои записи = 0» у Елены при 12 бронях в API — **dev-transient chunk-ошибка** («Invalid or unexpected token»), на чистом reload 12 строк; класс уже в do-not-refile.
- «Инвайт-диалог закрылся без запроса», «Подтвердить — мёртвая кнопка» — **мои ошибки скоупинга снапшота** (порталы `ModalSurface` живут вне `page-main`); на деле диалоги были открыты и работали. В файл не попали.
- «Cap не сработал» при первом прогоне — **300-секундный кэш плана** (`plan:current:*`) после DB-свапа мимо приложения; все продуктовые пути смены плана зовут `invalidatePlanCache` (проверено по call-sites) — не баг. Чистый повтор: блок сработал.
- «0 слотов у Ирины по всем услугам» — баг моего пробника (потерян фолбэк на `data.slots`); raw API отдаёт слоты.
