# Переезд медиа на Cloud.ru Object Storage (S3)

> Статус: **runbook для DevOps**, код готов. Составлен 2026-09-13.
> Смежное: `docs/DEPLOYMENT-ARCHITECTURE.md` §7.2 (аудит портируемости),
> `DEPLOY-BACKLOG.md` (операционные шаги дня деплоя).

---

## 0. Короткий ответ

**Кода менять не нужно.** Хранилище уже за интерфейсом `StorageProvider`, а
S3-реализация полностью env-driven: `@aws-sdk/client-s3`, статические
access-key/secret, path-style, никаких Yandex-специфичных SDK и никаких
дефолтов endpoint/region в коде (`src/lib/media/storage/s3.ts`).

Переезд состоит из трёх вещей:

| | Что | Кто |
|---|---|---|
| **A** | Завести бакет и сервисный аккаунт в Cloud.ru, получить ключи | DevOps/владелец |
| **B** | **Скопировать объекты с сохранением ключей 1:1** | DevOps |
| **C** | Переключить 5 переменных окружения и передеплоить | DevOps |

🔴 **B обязателен и необратим по последствиям пропуска.** Приложение резолвит
байты в момент запроса по `MediaAsset.storageKey`. Переключить env, не
скопировав объекты, — это «все аватары, обложки, портфолио и вложения чата
отдают 404» при полностью целой базе.

## 1. Что именно нужно получить у Cloud.ru

Пять значений, все — из консоли Cloud.ru. **Не угадывайте endpoint по памяти:**
у Cloud.ru несколько продуктовых линеек объектного хранилища (Evolution и
Advanced, унаследованная от SberCloud), и адрес S3-шлюза у них разный.
Возьмите его на странице бакета — в консоли он подписан как endpoint / точка
подключения S3.

| Переменная | Где взять | Примечание |
|---|---|---|
| `S3_ENDPOINT` | Консоль → Object Storage → бакет → параметры подключения | Полный URL со схемой `https://`. Без имени бакета в пути. |
| `S3_REGION` | Там же | Если провайдер региона не называет — поставьте `ru-central-1`; подпись SigV4 требует непустую строку, и она обязана совпадать с ожидаемой шлюзом. |
| `S3_BUCKET` | Имя созданного бакета | |
| `S3_ACCESS_KEY` | Сервисный аккаунт → статические ключи доступа S3 | Показывается один раз. |
| `S3_SECRET_KEY` | Там же | |

`S3_PUBLIC_URL` **оставьте пустым.** Медиа отдаётся через собственный роут
`GET /api/media/file/[id]` (ACL, приватность вложений чата — инв. #26), прямая
раздача из бакета в рантайме не используется.

### Требования к бакету

1. **Доступ — приватный.** Публичное чтение включать НЕ нужно и вредно:
   приватность вложений чата и клиентских фото держится на `ensureCanReadMedia`,
   а публичный бакет её обходит.
2. **Статические ключи (SigV4)**, не IAM-токены с TTL — клиент их не обновляет.
3. **Path-style адресация** (`https://<endpoint>/<bucket>/<key>`) — клиент ходит
   только так (`forcePathStyle: true`).
4. **Размещение в РФ** — это вход в ответ РКН по 152-ФЗ ст. 18 ч. 5
   (`RKN-COMPLIANCE-REPORT.md` § локализация). Зафиксируйте регион письменно.

### Про checksum-заголовки — уже закрыто кодом

`@aws-sdk/client-s3` начиная с 3.729 по умолчанию дописывает каждому `PutObject`
заголовки `x-amz-checksum-crc32` / `x-amz-sdk-checksum-algorithm`, и часть
S3-совместимых шлюзов отвечает на них `400`. Симптом: **каждая** загрузка медиа
падает при правильных ключах, а ошибка выглядит как проблема прав.

Клиент настроен `requestChecksumCalculation: "WHEN_REQUIRED"`
(`src/lib/media/storage/s3.ts`) — заголовки не отправляются. Отдельной
env-ручки нет намеренно: значение верно и для AWS, и для Yandex, и для Cloud.ru.

## 2. Копирование объектов (шаг B)

**Ключи должны совпасть байт в байт.** Переименование, добавление префикса,
«сложим в папку `media/`» — любое из этого ломает резолв.

Инструмент — `rclone` (умеет S3↔S3 напрямую, проверяет размер/хеш, умеет
докопировать изменившееся вторым проходом).

```bash
# ~/.config/rclone/rclone.conf
[src]
type = s3
provider = Other
endpoint = https://storage.yandexcloud.net
region = ru-central1
access_key_id = <старый ключ>
secret_access_key = <старый секрет>
force_path_style = true

[dst]
type = s3
provider = Other
endpoint = <S3_ENDPOINT из консоли Cloud.ru>
region = <S3_REGION>
access_key_id = <новый ключ>
secret_access_key = <новый секрет>
force_path_style = true
```

```bash
# 1) сухой прогон — убедиться, что ключи переносятся 1:1, без префиксов
rclone copy src:<старый-бакет> dst:<новый-бакет> --dry-run --max-depth 2 -v

# 2) основной прогон
rclone copy src:<старый-бакет> dst:<новый-бакет> \
  --transfers 16 --checkers 32 --s3-no-check-bucket --progress

# 3) сверка: пусто = наборы совпали
rclone check src:<старый-бакет> dst:<новый-бакет> --size-only
```

Альтернатива, если rclone недоступен: `aws s3 sync s3://old s3://new
--endpoint-url …` двумя профилями (скачать → залить). Медленнее и требует места
на диске; результат тот же.

### Сверка с базой (обязательная, до переключения)

Число объектов в бакете сравнивается с числом живых ассетов в БД:

```sql
SELECT count(*) FROM "MediaAsset" WHERE "deletedAt" IS NULL;
```

```bash
rclone size dst:<новый-бакет>
```

Расхождение вниз — стоп, не переключайтесь. Расхождение вверх допустимо
(мягко удалённые строки + объекты, чьи строки уже вычищены).

## 3. Переключение (шаг C)

1. **Окно.** Между последним `rclone copy` и рестартом приложения загруженные
   файлы попадают в СТАРЫЙ бакет. Либо включите страницу «идут работы»
   (`maintenance`-профиль compose, MAINTENANCE-PAGE-01) на время последнего
   прохода, либо после рестарта прогоните `rclone copy` ещё раз в ту же сторону
   — он докопирует только новое.
2. Обновите в prod-env пять переменных (§1). `STORAGE_PROVIDER=s3` не меняется.
3. Передеплой. Переменные читаются **на сервере в рантайме**
   (`src/lib/env.ts`) — пересборки образа ради них не нужно, нужен рестарт
   контейнеров `web`, `api` и **worker** (воркер удаляет объекты по задаче
   `media.purge` и ходит в то же хранилище).
4. Приёмка — не «страница открылась», а четыре проверки:
   - старое фото портфолио открывается (проверяет копирование);
   - **новая** загрузка аватара проходит (проверяет ключи + checksum-совместимость);
   - удаление медиа не оседает в dead-letter (`/api/health/worker`, задача
     `media.purge` — проверяет права на `DeleteObject`);
   - вложение чата открывается участнику и **не открывается** постороннему
     (проверяет, что бакет не сделали публичным).
5. Старый бакет **не удаляйте** минимум до конца окна отката. Откат = вернуть
   пять прежних значений и рестартовать; данные в старом бакете к этому моменту
   целы, потому что `copy` (в отличие от `move`) источник не трогает.

## 4. Что НЕ нужно трогать

- **Остальные Yandex-интеграции остаются.** YandexGPT, эмбеддинги и vision
  визуального поиска, Геокодер/Suggest, Yandex ID OAuth — это вызовы API по
  интернету, они не зависят от того, где лежат файлы и где хостится приложение
  (`DEPLOYMENT-ARCHITECTURE.md` §7.1). Мигрировать их «заодно» не нужно.
- **Аллоулист хостов `next/image`** (`next.config.ts` + `src/components/ui/image-host.ts`,
  держатся синхронно) — там `storage.yandexcloud.net`. Трогать **не нужно**:
  новые `mediaUrl` относительные, картинки идут через same-origin-прокси.
  Хост нового провайдера добавляется в ОБА файла только если вы решите
  раздавать медиа напрямую из бакета/CDN — то есть вместе с заполнением
  `S3_PUBLIC_URL`, чего этот runbook не предполагает.
- **Легаси абсолютные `mediaUrl`.** В коде их больше не создают; если в
  прод-базе такие строки найдутся (`WHERE "mediaUrl" LIKE 'http%'`), их объекты
  скопируются обычным `rclone copy` вместе со всеми, но САМИ СТРОКИ продолжат
  указывать на старый хост — их нужно либо переписать на относительный вид,
  либо оставить старый бакет живым. Посчитайте их до переезда.
