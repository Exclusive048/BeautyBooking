## 2. Находки

### 🟡 Ф-1 — `?vk=<исход>` не доходит до пользователя в клиентском кабинете

**Что.** FIX-B14 сделал стартовую ногу VK навигационной: при отказе браузер возвращается на страницу-источник с `?vk=<исход>`, и сообщение показывает `VkNotificationsSection`. В **клиентском** кабинете кнопка подключения VK есть, а потребителя `?vk=` нет — пользователь возвращается на страницу без объяснения.

**Доказательство — путь, а не результат.** Навигация на `/cabinet/profile?vk=provider_unavailable` и `?vk=start_failed`, ожидание 11 с:

```
[provider_unavailable] url-now: ?vk=provider_unavailable   ← параметр НЕ снят
[provider_unavailable] matched lines: []
[start_failed]         url-now: ?vk=start_failed            ← параметр НЕ снят
[start_failed]         matched lines: []
```

Эффект в `vk-notifications.tsx:72-81` снимает параметр через `replaceState` **только когда выставил ошибку**. Параметр на месте ⇒ ветка не выполнялась. Это наблюдаемый признак пути, а не вывод из пустого экрана.

**Механизм.** `VkNotificationsSection` рендерит только `studio-cabinet/settings/.../notifications-section.tsx`. `client-cabinet/profile/client-profile-page.tsx` его **не** рендерит (греп: 0 вхождений), но имеет собственную кнопку (`T.linkedAccounts.vkConnect`, строка 611) и читает `?vk=` **ноль раз** (`grep -c 'location.search|"vk"'` → `0`).

**Ирония.** Комментарий самого FIX-B14 обещает: «сообщение появляется на любой странице с этой кнопкой без per-page плюмбинга» и называет риск — «плюмбинг разошёлся бы ровно там, где кнопку добавят следующей». Это уже произошло.

**Ограничение метода.** Настоящий отказ провайдера не воспроизводился (нужен падающий VK); параметр подставлялся напрямую — но именно его механизм FIX-B14 и потребляет, так что предмет проверки тот самый.

### 🟡 Ф-2 — `clearOtpRateLimit` из committed-харнесса больше не чистит IP-счётчик

**Что.** `.qa/otp.ts` удаляет ключ `otp:request:ip:sha256("unknown")`, опираясь на комментарий «на localhost XFF нет → `extractClientIp` вернёт null → продукт хеширует строку "unknown"». Продукт так больше не делает.

**Замер.**

```
живой ключ:              otp:request:ip:eff8e7ca…  = 1 (ttl 17s)
harness удаляет:         otp:request:ip:b23a6a84…      ← sha256("unknown")
sha256("::1")          = otp:request:ip:eff8e7ca…      ← совпадает с живым
sha256("::ffff:127.0.0.1") = otp:request:ip:3e48ef9d…
```

Совпадения нет ⇒ IP-счётчик (5/60 с, общий на оба канала) не снимается никогда. Серия холодных логинов упирается в 429, и по симптому это неотличимо от «сломался логин» — ровно тот класс, что скилл `playwright-qa` называет «OTP-login таймауты».

**Побочно наблюдался и второй потолок SEC-26:** `otp:request:phone:d5dd49…` с `ttl 3557s` — почасовой предел на идентичность. Его харнесс чистит корректно (форма ключа совпадает).

**Обход в этом прогоне:** прямое удаление `otp:*` из Redis.

### 🔵 Ф-3 — `slotLabel` пакетных броней хранит сырой ISO вместо человеческой метки

**Замер** (одна таблица, четыре строки):

| путь | `slotLabel` |
|---|---|
| одиночная бронь (виджет студии) | `2026-08-14 18:00` |
| одиночная бронь (`/api/bookings`) | `2026-08-19 12:00` |
| компонент соло-пакета | `2026-08-20T07:00:00.000Z` |
| компонент студийного пакета | `2026-08-20T05:00:00.000Z` |

**Почему 🔵, а не выше.** Проверено грепом: `slotLabel` в `.tsx` встречается только как **записываемое** значение (тела запросов, локальный state `reschedule-modal`); ни один список/журнал его не рендерит — время выводится из `startAtUtc` через salon-tz форматтеры. То есть это гигиена данных, а не видимый дефект. Но поле переживает перенос **не обновляясь** (после move 12:00→14:00 `slotLabel` остался `12:00`), поэтому любой будущий потребитель, взявший его за отображение, получит расхождение.

## 2b. Исследованные и **исключённые** ложные срабатывания

Обе поймал повторным замером; записываю, потому что «зелено с первого раза» здесь ничего не значило бы.

**(1) «Клиент не видит свои записи» — НЕТ.** Первые прогоны показывали `/cabinet/bookings` с `Все 0 / Предстоящие 0` и KPI «—», при 12 бронях в БД; сетевой лог видел только `/api/cities`. Выглядело как 🔴. При ожидании **12 с** страница делает `200 /api/cabinet/user/bookings?status=all` и рендерит **12 строк**.
**Ограничение метода:** `npm run dev` компилирует маршрут по первому обращению, а данные идут SWR-запросом после гидратации; окна 2.5 с и 9 с ловили страницу до его разрешения. В логе видны `ERR_ABORTED` на `/api/me`, `/api/cabinet/user/profile`, `/api/notifications/stream` — прерванные навигацией запросы, которые SWR затем повторил. **Вывод для следующего прохода: на холодном dev-маршруте окно ожидания ≥ 12 с, иначе пустая страница читается как дефект.**

**(2) «Отозванная сессия продолжает отдавать ПДн» — НЕТ.** После `/logout` тот же access-токен получал `200` на `/api/me`. Проверка тела и второй поверхности развела случаи:

```
token fid = 7cc4d833…   семья: одна строка, active = f  (отозвана)
GET /api/cabinet/user/bookings → 401          ← SEC-13 работает
GET /api/me                    → 200 {"ok":true,"data":{"user":null}}   ← данных нет
```

`/api/me` — эндпоинт «кто я», и `user: null` есть его штатный ответ неаутентифицированному. Утечки нет; логаут отзывает семью (`revokedAt` проставлен), куки гасятся `Max-Age=0`.

## 3. Живые измерения, заменяющие стендовые

**Это главный раздел прогона.** Ниже честно разделено, что теперь измерено вживую, а что остаётся выведенным.

### 3.1. Воронка при обрыве — репродукция 🔴 (было `500`)

| Эндпоинт | SMOKE-01 / FIX-C10 (замер) | **SMOKE-02, живой** |
|---|---|---|
| `/api/public/providers/{id}/slots` | **500** `INTERNAL_ERROR` | **200**, данные корректны |
| `…/booking-days` | **500** | **200** |
| `/api/masters/{id}/availability` | **500** | **200** |
| `/catalog` (просмотр) | 200 | 200 |

Данные не просто «200»: `startAtUtc 05:00Z` → метка `2026-08-17 10:00`, то есть GMT+5 салона сохранён при обрыве.

**В браузере воронка тоже жива:** полоса дней рендерится, слот-пикер показывает «Время салона (Екатеринбург, GMT+5)», кнопка отправки достижима — то, чего гость не мог достичь до FIX-C11.

### 3.2. Размыкатель — живые числа против стендовых

Стендовые числа FIX-C4 («~5 с обнаружение, дальше нормально») **подтверждены живым Redis** и теперь заменяются на измеренные:

| Момент | **Живой замер (SMOKE-02)** | Было в runbook (стенд FIX-C4) |
|---|---|---|
| Запрос 1 после падения | **7.63 с** | «до 5 с» |
| Запрос 2 | **2.61 с** | — |
| Запрос 3 и далее | **0.099 / 0.073 / 0.115 с** | «примерно нормально» |
| Восстановление, t+0 с | **2.15 с** (проба + холодный кэш) | — |
| Восстановление, t+6 с | **0.047 с** (кэш прогрет) | — |

**Обнаружение стоит дороже, чем обещал runbook: 7.63 + 2.61 ≈ 10.2 с на две первые страницы, а не «до 5 с».** Причина согласуется с устройством: порог `CONSECUTIVE_TIMEOUTS_TO_OPEN = 2`, то есть два полных дедлайна по 2.5 с плюс несколько команд первого запроса. Форма поведения та, что описана; величина занижена. Runbook исправлен этим же изменением (§5).

**Сравнение с до-размыкательными живыми числами SMOKE-01 (F5):** 9.2 / 14.0 / 20.9 с на витрине → теперь после двух первых запросов **десятые доли секунды**. Улучшение реально и измерено вживую, а не выведено.

### 3.3. Гостевые пути записи — форма отказа и дельта строк

Все четыре пишущих входа, Redis остановлен:

| Путь | HTTP | Код | Сообщение |
|---|---|---|---|
| `POST /api/bookings` | **503** | `RATE_LIMIT_UNAVAILABLE` | «Сервис временно недоступен. Попробуйте позже.» |
| `POST /api/public/bookings` | **503** | `RATE_LIMIT_UNAVAILABLE` | то же |
| `POST /api/public/packages/{id}/book` | **503** | `RATE_LIMIT_UNAVAILABLE` | то же |
| `…/packages/{id}/studio/book` | **503** | `RATE_LIMIT_UNAVAILABLE` | то же |

**Дельта строк — ноль по всем четырём:** `Booking|UserProfile|UserConsent|BookingPackage` = `166|89|35|0` до и `166|89|35|0` после. Политика (fail-closed) не изменилась; изменился сигнал — раньше три публичных отвечали 429 «Слишком много запросов» на первый запрос гостя.

### 3.4. Чат

`POST /api/chat/threads/{slug}/messages` при обрыве: **503 `RATE_LIMIT_UNAVAILABLE`**, не «Слишком много сообщений». Контроль с живым Redis: **201**.

### 3.5. Замок под конкуренцией

8 параллельных запросов слотов при обрыве: **все 200**, время 5.08–7.45 с, **payload побайтно идентичен у всех восьми** (один `md5`). Ни зависания, ни дедлока, ни устаревших данных. Цена деградации — дублированный расчёт, как и задумано.

### 3.6. Пробы здоровья — измерено, не выведено

### 🚨 Pre-launch risks to watch

- **Работает в тестах, но не в браузере — один подтверждённый случай:** `?vk=`-сюрфейсинг (Ф-1). Механизм FIX-B14 покрыт сторожем на уровне роутов (`oauth-start-navigation.test.ts` проверяет, что нога отвечает навигацией), но **потребителя параметра на конкретной странице не проверяет никто**. Класс: «сервер отдал правильный сигнал, страница его не читает» — тот же, что `CLIENT-ERROR-MESSAGE-PASSTHROUGH-SWEEP`, только для навигационных исходов.
- **Инструментальный риск:** харнесс, которым проверяют продукт, сам протух (Ф-2) — и протух молча, отдавая 429, неотличимый от поломки логина. Перед деплойным прогоном это чинить первым, иначе каждый следующий живой проход будет тратить время на ложный след.
- **Метод:** на холодном `npm run dev`-маршруте окно ожидания < 12 с даёт ложные «пустая страница / данных нет». Два таких срабатывания в этом прогоне (§2b). Для деплойного прогона на прод-сборке этого класса быть не должно, но проверять надо тем же способом — по сетевому логу, а не по глазам.
- **Незакрытая асимметрия F7:** к мастеру студии нельзя записаться с его собственной страницы. Это не деградация от обрыва и не блокер деплоя, но это потерянная конверсия на живом трафике.
