### 1b. Убрать реестр контейнеров из системы — сборка на ВМ (решение владельца 2026-08-07)

Сейчас workflow `Deploy to Production` падает на каждом пуше в шаге `Login to Yandex Container Registry` (`Error: Password required` — секрета нет, площадка не выбрана). Пять дней красного CI обесценивают и те гейты, что добавляются пунктом 1. Решение владельца: **реестр контейнеров не используем вообще**, образы собираются на самой прод-ВМ.

**Убрать из системы:**
- Из workflow — логин в реестр, `build and push` для app и worker, все ссылки на `cr.yandex`/`YC_REGISTRY_ID`/`YC_SA_JSON_KEY`.
- Из `docker-compose.prod.yml` — `image: cr.yandex/...` заменить на `build:` с контекстом репозитория (или на локальный тег, собираемый скриптом деплоя, — выбрать по факту устройства файла и обосновать).
- Из `DEPLOY_GUIDE.md`, `DEPLOY-BACKLOG.md`, снапшота — все шаги про создание реестра, сервисный аккаунт с ролями pusher/puller и связанные секреты. Открытый вопрос §0 «cr.yandex vs cloud.ru» в части реестра закрывается: реестра нет; вопрос о площадке ВМ остаётся.

**Новая схема CI/CD — три независимые части:**
- **`ci.yml` — качество.** PR + push в рабочие ветки. Вся батарея `npm run check` (18 шагов, п.1) + `npm run test`. **Секретов не требует.** Если какой-то шаг требует — это отдельная находка, назвать её.
- **Проверка сборки в CI.** `docker build` для app и worker **без публикации** — доказывает, что Dockerfile жив и образ собирается. Секретов не требует. Кэш слоёв GitHub Actions включить, иначе шаг будет долгим.
- **`deploy.yml` — деплой на ВМ.** Только `workflow_dispatch` (ручной запуск) + job-level `if` на наличие секретов ВМ, чтобы до провижининга он был «пропущен», а не «упал». Содержимое: SSH на ВМ → `git pull` в `/opt/masterryadom` → **тегирование текущего образа как `:previous`** → `docker compose build` → `docker compose run --rm migrate` → `docker compose up -d` → healthcheck → при неуспехе healthcheck откат на `:previous`.

**Обязательное для схемы «сборка на ВМ»:**
1. **Ограничение ресурсов сборки** — сборка идёт рядом с работающим приложением. Задать лимиты (`--memory`, при необходимости `--cpus`) и проверить, что при сборке приложение продолжает отвечать. Замер в отчёте: свободная память до/во время сборки.
2. **Откат без реестра** — перед сборкой текущий рабочий образ тегируется `:previous`; в деплой-док добавить точную команду отката (переключение на `:previous` + `up -d`). Это единственная замена реестрового отката, поэтому она должна быть проверена, а не описана.
3. **Сборка в две стадии, не на лету** — сначала `build`, только потом `up -d` с готовым образом; downtime не должен растягиваться на время сборки.
4. **Исходники на ВМ** — теперь на прод-машине лежит репозиторий. Проверить, что `.env` не перезаписывается `git pull`, что рабочее дерево не содержит артефактов сборки в git, и зафиксировать это в деплой-доке.
5. **Обновить actions**, дающие Node 20 deprecation warning (видно в логе прогона #62).

**Приёмка:** пуш в ветку → зелёный `ci` (гейты + тесты) и зелёная проверка сборки образов, **без единого секрета**; `deploy` в списке прогонов отсутствует или помечен пропущенным, а не упавшим. Проверить фактически (открыть прогон), а не по тексту yml.
**Приёмка:** намеренно сломанный PR-кандидат (английская ошибка / `process.env[…]` / DROP защищённого объекта) валит CI. Проверить, а не предположить.
