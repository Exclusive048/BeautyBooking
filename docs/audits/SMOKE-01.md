## 2. Находки

### 🔴 F1 — Брони из публичного виджета студии неуправляемы из кабинета студии

**Что.** Бронь, созданную через собственную публичную страницу записи студии, кабинет студии **показывает в журнале, но не может ни перенести, ни переназначить мастера**: любое действие отвечает `404 BOOKING_NOT_FOUND` / «Запись не найдена.»

**Воспроизведение.**
1. `/u/vision-studio/booking?master=vision-marina-lebedeva-1` → выбрать услугу, слот, заполнить контакты, «Записаться». Бронь создаётся (201).
2. Войти как Виктория (`+79992000000`) → `/cabinet/studio/bookings`. Бронь **видна** в журнале.
3. `…` → «Перенести по времени» → любое время → «Перенести».
4. Диалог показывает **«Запись не найдена.»**, консоль — `404` на `PATCH /api/studio/bookings/<id>/move`. Время не меняется.

**Доказательство причины — контрольный эксперимент.** Один и тот же эндпоинт, одна сессия, одна студия, тот же целевой мастер и время, различается только наличие `studioId`:

```
widgetBooking  (studioId = NULL) → 404 BOOKING_NOT_FOUND
seededBooking  (studioId  set  ) → 200 OK
```

Бронь, созданная **из кабинета** («Новая запись»), получает `studioId` и переносится нормально (200).

**Механизм.** `moveStudioBooking` → `assertBelongsToStudio("booking", …)` (`src/lib/studio/tenancy.ts:80`) скоупится `where: { id, studioId }`. Публичный путь идёт `POST /api/bookings` → `createBooking` (`src/lib/bookings/createBooking.ts`), и **`studioId` там не выставляется вообще** — слова `studioId` в файле нет. Журнал при этом скоупится по `providerId`, поэтому бронь видна: расхождение между «что показываем» и «что можем изменить».

**Состояние БД (dev):** 59 из 60 броней Vision несут `studioId`; единственная без него — созданная виджетом в этом прогоне. По всем студиям: 62 с `studioId`, 6 без (5 сидовых + моя).

**Почему это не поймали построением.** Юнит-тесты и сиды строят брони с уже проставленным `studioId`; путь виджета — единственный, который его не ставит, и он проходит через общий `createBooking`, у которого поля просто нет в контракте. Ни один гейт не сверяет «кто создал» с «кто может изменить».

**Побочно:** та же бронь показана в колонке `ИСТОЧНИК` как **«Звонок»** (`source = MANUAL`) — онлайн-запись самообслуживанием подписана как телефонная.

### 🔴 F2 — `GET /api/health` при обрыве Redis не отвечает никогда

**Что.** Runbook (`docs/runbooks/redis-down.md:5`) обещает: «`GET /api/health` возвращает `503` и `{ ok: false }`». Фактически при остановленном Redis эндпоинт **не завершается**.

**Доказательство — длительность ответа равна таймауту клиента, а не свойству сервера:**

| `curl -m` | что залогировал сервер |
|---|---|
| 10 с | `GET /api/health 200 in 10.0s (application-code: 7.5s)` |
| 30 с | `GET /api/health 200 in 30.0s (application-code: 27.5s)` |
| 90 с | `GET /api/health 200 in 90s (application-code: 87s)` |
| 240 с | `GET /api/health 200 in 4.0min (application-code: 4.0min)` |

Тело не получено ни разу (`http_code = 000` у curl во всех четырёх прогонах). Проверка идёт по коду возврата и по времени, а не по тексту: **сколько ждёт клиент — столько и «работает» хендлер.**

**Почему это важнее, чем выглядит.** `/api/health` — первичный сигнал в runbook'е, и он же используется как healthcheck в деплое (`deploy.yml`, автооткат на `:previous`). Эндпоинт, который при аварии зависает вместо `503`, означает: (а) дежурный по runbook'у не получит описанного симптома, (б) healthcheck деплоя упрётся в свой таймаут — то есть автооткат сработает по таймауту, а не по честному «сервис нездоров», и (в) любой ALB-health-probe будет висеть.

⚠️ **Замечание о границах:** `RES-01` (`withRedisCommandTimeout`) ограничивает **команды**; здесь висит не команда, а, судя по логам, цикл переподключения (`Redis client reconnecting` / `Redis client error` каждые ~2 с без конца). Верхней границы у самого хендлера нет.

### 🟠 F3 — Курируемое сообщение о денежном потолке ИИ до пользователя не доходит

**Что.** FIX-B16 завёл строку `UI_TEXT.ai.dailyLimitReached` — «Функция сегодня недоступна — дневной лимит ИИ-запросов исчерпан. Попробуйте завтра.» Она корректно уходит на проводе. **Единственная достижимая из UI ИИ-поверхность её выбрасывает** и показывает вместо неё «**Резюме временно недоступно. Попробуйте через минуту.**»

**Воспроизведение.** Поднять `AiSpendCounter` метра `review-summary` до 500 на сегодняшний UTC-день, очистить `ai:review-summary:*` в Redis, открыть `/u/anna-sokolova`, нажать «Показать резюме».

**Что на проводе:** `429`, `{"code":"AI_DAILY_LIMIT_REACHED","message":"Функция сегодня недоступна — дневной лимит ИИ-запросов исчерпан. Попробуйте завтра."}`
**Что на экране:** «Резюме временно недоступно. Попробуйте через минуту.» (скриншот `B3`)

**Механизм.** `reviews-preview.tsx:186` — `if (!res.ok || …) throw new Error(t.summaryFailed)`, затем `catch { setSummaryError(t.summaryFailed) }`. Тело ответа не читается ни в одной ветке, то есть код `AI_DAILY_LIMIT_REACHED` не различается.

**Почему это не косметика.** Сообщения расходятся не тоном, а **масштабом времени**: продукт советует повторить «через минуту», тогда как потолок сбрасывается в UTC-полночь. Пользователь будет жать кнопку весь день.

### 🟠 F4 — На экране успеха гостевой брони отсутствует имя мастера

**Что.** После успешной брони у solo-мастера заголовок карточки рендерится как **`" ждёт вас"`** — с ведущим пробелом и без имени. Шаблон `UI_TEXT…successHeadlineTemplate = "{name} ждёт вас"` подставляет пустую строку.

**Доказательство:** `document.querySelector` по абзацу вернул ровно `" ждёт вас"`; при этом `GET /api/public/bookings/<id>` в том же браузере отдаёт `provider.name = "Анна Соколова"` — то есть источник данных исправен, не доезжает подстановка.

**Механизм.** `booking-flow-stepper.tsx:408` ставит `providerName: ""` с комментарием «populated by URL refresh fetch below»; обогащающий `fetch` существует, но результат до заголовка не доходит (наблюдалось в течение всей сессии, не гонка первых миллисекунд).

**Смежно (🟡):** URL `?bookingId=<id>`, который приложение само пишет в адресную строку, **не восстанавливает карточку подтверждения** — при перезагрузке панель показывает «Выберите услугу, чтобы записаться». То есть ссылку на своё подтверждение пользователь потерять может, а вернуться по ней — нет.

**Контраст:** экран успеха **студийного** виджета корректен и полон: «Вы записаны! / Маникюр классический · Марина Лебедева · чт, 13 авг. · 14:00 (Екатеринбург, GMT+5)» — с именем и меткой зоны (скриншот `A2`).

### 🟡 F6 — `Retry-After` у отказа денежного потолка отсутствует на проводе

Контекст §11 и инв. #44 описывают отказ как «429 `AI_DAILY_LIMIT_REACHED` + `Retry-After` до конца UTC-суток». Измерено: заголовка **нет**, и в `error.details` секунд тоже нет.

`AiSpendCeilingError` (`spend-ceiling.ts:132`) принимает `retryAfterSeconds` и хранит его полем, но в `AppError` его не передаёт; `secondsToUtcMidnight` вне самого модуля и его тестов не имеет ни одного потребителя (проверено грепом). То есть значение вычисляется и никуда не едет.

Тот же класс наблюдается у `429 RATE_LIMITED` от `/api/address/suggest` — `Retry-After` тоже отсутствует (у прокси-тира он есть, у роутов со своим лимитером — нет).

### 🔵 F9 — Три из четырёх «ИИ-поверхностей» не имеют потребителя в UI

Контекст §11 перечисляет четыре chat-поверхности под денежным потолком. Грепом по `src/` (исключая `app/api` и тесты) потребитель нашёлся **только у одной** — `review-summary` (`features/public-profile/master/reviews-preview.tsx:179`). У `suggest-description`, `suggest-reply` и `/api/master/advisor` вызывающих в UI нет; `lib/advisor/*` импортируется только собственными роутами. Строка `UI_TEXT…suggestReply: "Предложить ответ"` существует под неподключённую кнопку.

Это не дефект потолка — гейт `paid-call-coverage.test.ts` честно доказывает, что каждый вызов чокпойнта учтён. Но он ничего не говорит о **достижимости**, поэтому операционно «защищены четыре поверхности» сегодня означает «одна достижимая и три спящих». Для оценки суточных потолков перед флипом (строка в `DEPLOY-BACKLOG §5`) это меняет арифметику.

### 🔵 F10 — Локальный `.env` уводит logout и OAuth-редиректы на чужой домен

`/logout` на localhost редиректит на `https://beautyhub.art/` (Cloudflare 530). Причина — `APP_PUBLIC_URL=https://beautyhub.art` в **untracked** локальном `.env`; `getPublicOrigin` осознанно предпочитает сконфигурированный origin заголовкам запроса (SECURITY-EXPOSURE-AUDIT-01 · B4). Отслеживаемые шаблоны **корректны** (`.env.example` → localhost, `.env.production.example` → `мастеррядом.online`).

**Это находка среды, а не продукта** — и записана именно поэтому: сессия при этом гасится правильно (после редиректа `/cabinet/*` отдаёт `/login`), но локально невозможно пройти post-logout экран, а `?error=`-ключи OAuth-старта приходится проверять открывая `/login?error=…` вручную. Вероятно, ровно поэтому эти пути и не были размяты раньше.
