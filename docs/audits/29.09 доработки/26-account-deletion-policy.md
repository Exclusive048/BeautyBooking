**Источник:** `RKN-FIX-03-B` (BACKLOG, раздел E юрпакета и 🔴 пункт) · **Тип:** нужно решение (юрист) + доработка · **Объём:** M
**Зависит от:** — (фоновая анонимизация «через N месяцев» делит механизм с retention `RKN-FIX-04`, но не ждёт его)

## Что не так

Удаление аккаунта — `deleteUserAccount` (`src/lib/deletion/delete-account.ts:17-173`): строка `UserProfile` анонимизируется, связи чистятся по карте `USER_RELATION_DISPOSITION` (`src/lib/deletion/user-data-disposition.ts:49-211`). DMMF-сторож (инв. #35) держит полноту карты. У **восьми** связей статус `POLICY_PENDING` — сегодня они переживают удаление целиком:

| Связь (поле `UserProfile`) | Что остаётся после удаления | Предложение | Нужен юрист? |
|---|---|---|---|
| `bookings` (`booking.prisma`: `clientName`, `clientPhone` NOT NULL, `clientNameSnapshot`, `clientPhoneSnapshot`, `comment`, `referencePhotoAssetId`) | имя и телефон в истории мастера/студии; своя реплика клиента; фото-референс | прошедшие записи — **анонимизировать сразу**: имя → «Удалённый пользователь», телефон → пустая строка, снимки и `comment` → null, фото `BOOKING_REFERENCE` — в очистку; время, услуга, цена и статус остаются (выручке и аналитике мастера личность не нужна) | да — вопрос 1 |
| `bookingPackages` | только id и связи, ПДн нет | **хранить** как есть | нет |
| `notifications` | удаляются только строки **старше** 30 дней (`delete-account.ts:11,82`); свежие живут вечно, фоновой чистки нет | **удалить все**: получателя больше нет, читать их некому | нет (подтвердить) |
| `consents` (`UserConsent`: версия, `agreedAt`, `revokedAt`, IP, User-Agent) | вся история согласий | **хранить 3 года** после удаления (доказательство законности обработки), потом удалять фоновым проходом | да — вопрос 2 |
| `reviewsAuthored` (`Review.text`) | публичный текст; автор уже показан «Удалённый пользователь» | **хранить** (рейтинг мастера не меняется) + в окне удаления галочка «Удалить и мои отзывы» | да — вопрос 3 |
| `clientCards` (`ClientCard.clientPhone`, `notes`, `tags`, фото `CLIENT_CARD_PHOTO`) | карточка мастера о человеке, в т.ч. возможны сведения о здоровье (аллергии) | **удалить** карточку и фото | да — вопрос 4 |
| `clientNotes` (`ClientNote.text`) | заметки мастера о человеке | как `clientCards` | да — вопрос 4 |
| `modelApplications` (`clientNote`, `proposedTimeLocal`, фото `MODEL_APPLICATION_PHOTO`) | отклики на модель-офферы с текстом и фото | без брони — **удалить**; с бронью — `clientNote` → null, фото в очистку, дальше как `bookings` | нет (следует за 1) |

**Теневые данные — в карте их нет:** это не связи `UserProfile`, поэтому DMMF-сторож их не видит.
- `ChatMessage.senderName` / `body` и вложения `CHAT_ATTACHMENT` (висят на `BookingChat` → `Booking`). Предложение: `senderName` → «Удалённый пользователь»; судьба `body` — вопрос 5.
- 🔴 **`OtpCode` с почтой не удаляется никогда.** Удаление чистит коды только по телефону (`delete-account.ts:72-74`), профиль читается с одним `phone` (`:22`), а других `otpCode.deleteMany` в `src/` нет. Строки с адресом почты в открытом виде переживают удаление и живут вечно. Это инженерный дефект, решение юриста не нужно.
- Приглашения в студию, адресованные человеку (`StudioInvite.phone`/`email`): в карте только отправленные им (`studioInvites`, RETAINED).
- Уведомления ДРУГИХ людей с его именем («Иван записался») — это данные мастера, их закрывает retention (`RKN-FIX-04`), не эта спека.

**Запись BACKLOG про медиа неточна.** «Достаточно расширить `PURGEABLE_KINDS`» — неверно. `collectAccountMedia` (`src/lib/media/purge.ts:75-85`) отбирает только `entityType: USER` и `createdByUserId` = удаляемый. Фото карточки клиента загружает МАСТЕР, фото-референс привязан к брони. Для каждого вида нужен свой сборщик через связь: `ClientCardPhoto` → `card.clientUserId`, `Booking.referencePhotoAssetId`, `ChatMessage.attachmentMediaAssetId`, фото отклика. Механизм очистки (очередь `media.purge`, порядок «объект → строка») готов.

⚠️ **Не было в BACKLOG — будущие записи клиента.** Для кабинетов DELETION-03 блокирует удаление при живых записях, а для клиента проверки нет (`delete-account.ts:43-49` считает только записи мастера и студии). Клиент с визитом на завтра удаляет аккаунт — запись остаётся подтверждённой, мастер его ждёт, а напоминания уходят в центр уведомлений удалённого профиля.

## Что сделать

**Сейчас, без юриста.**
1. `delete-account.ts`: читать и `email`; удалять `OtpCode` по телефону **и** по почте (`OR`).
2. Удалять неотвеченные приглашения в студию, адресованные подтверждённому телефону или почте человека.
3. Политика в коде — `src/lib/deletion/account-deletion-policy.ts`: для каждой связи из таблицы действие `KEEP | DELETE | ANONYMIZE_NOW | ANONYMIZE_AFTER(months)`. Безопасное значение по умолчанию — **`KEEP`, то есть как сейчас**: удаление необратимо, и включать его до ответа нельзя. Функции всех действий написаны и покрыты тестами; включение — правка одной константы.
4. Сторож: карта диспозиций и политика не расходятся — у связи с `POLICY_PENDING` может быть только `KEEP`, у решённой — не `POLICY_PENDING`. Тем же изменением проставить новые `kind` в `user-data-disposition.ts`.
5. Сборщики медиа по видам (см. выше). Вид переносится из `POLICY_PENDING_KINDS` в `PURGEABLE_KINDS` — существующий тест не даст ему остаться в двух списках.
6. Отложенная анонимизация (`ANONYMIZE_AFTER`) — проход воркера раз в сутки по `UserProfile.isDeleted && deletedAt < now − N`. Миграция не нужна: `deletedAt` уже есть. Пачками, идемпотентно.
7. Будущие записи клиента — по ответу на вопрос 6.

**После ответов.** Выставить действия в политике, перевести `kind` в карте, поправить тексты окна удаления (`UI_TEXT`: что исчезнет, что останется у мастера) и `/privacy` (раздел о сроках) — последнее вместе с юристом.

## Решения владельца

1. **(юрист)** Записи: мастер/студия — самостоятельный оператор данных клиента или платформа обрабатывает их по поручению мастера? **А** — анонимизировать прошедшие записи сразу (рекомендация); **Б** — хранить 3 года (исковая давность, ст. 196 ГК РФ), потом анонимизировать; **В** — хранить бессрочно (мастер — оператор, его основание). Последствия: при А мастер теряет контакт по спорному визиту; при Б телефон удалённого человека ещё 3 года находится поиском по истории.
2. **(юрист)** `UserConsent` после удаления: сколько хранить и хранить ли IP/User-Agent. Рекомендация — 3 года целиком, затем удалить: без IP и времени согласие перестаёт быть доказательством.
3. **(юрист + владелец)** Отзывы: **А** — оставить с «Удалённый пользователь» (как сейчас); **Б** — А + галочка «Удалить и мои отзывы» с пересчётом рейтинга (рекомендация); **В** — удалять всегда. При В рейтинги мастеров прыгают от чужих решений.
4. **(юрист)** Карточки и заметки мастера о клиенте: **А** — удалить вместе с фото (рекомендация: в заметках возможны сведения о здоровье, а это особая категория, ст. 10); **Б** — хранить (мастер — оператор, инв. #25).
5. **(юрист)** Переписка: **А** — заменить текст сообщений клиента на «Сообщение удалено», вложения удалить (рекомендация); **Б** — хранить (вторая сторона — мастер).
6. **(владелец)** Будущие записи клиента при удалении: **А** — блокировать удаление с текстом «Сначала отмените предстоящие записи» и ссылкой на «Мои записи», как у кабинетов (рекомендация: мастер не ждёт человека, которого нет); **Б** — отменять автоматически с уведомлением стороны провайдера; **В** — как сейчас.
7. **(владелец)** Уведомления: удалять все сразу (рекомендация) — да/нет?

## Готово, когда
- После удаления нет `OtpCode` ни по телефону, ни по почте; нет адресованных человеку неотвеченных приглашений.
- Каждая связь из таблицы обрабатывается по политике; ни одна не осталась с `POLICY_PENDING` без явного `KEEP` в политике; медиа удаляются из хранилища.
- Поведение с будущими записями соответствует ответу на вопрос 6.

- Анонимизация необратима: включать только после письменного ответа юриста и со снимком БД на проде.
