# 07 · Окно записи на студийных путях и в модель-оффере

**Источник:** `BOOKING-WINDOW-STUDIO-PATHS` (BACKLOG) · **Тип:** нужно решение + доработка · **Объём:** M
**Зависит от:** —

## Что не так

Окно записи («минимум за N ч» / «максимум на N дней» / «не принимаю новых клиентов») проверяет
`assertBookingWindow` (`lib/bookings/policy-enforcement.ts:95`, для услуги студии — строже из двух,
`stricterBookingWindow` `:68`) и `assertAcceptsNewClient` (`:124`). ⚠️ Запись в BACKLOG приписывает
окну и `visibleSlotDays` — это неверно: видимые дни только режут выдачу `/slots`
(`clampVisibleSlotsHorizon`), при записи не проверяются. Карта путей, сверенная по коду 2026-09-29:

| Путь | Кто выбирает время | min/max | новые клиенты | «не в прошлом» |
|---|---|---|---|---|
| воронка, легаси-воронка, соло- и студийный пакет (`resolveBookingCore`) | клиент | ✓ `booking-core.ts:482` | ✓ `:483` (флаг провайдера) | ✓ (через min ≥ 0) |
| предложение переноса (`rescheduleBooking`, в т.ч. гость по ссылке) | сторона записи | ✓ `usecases.ts:257` | не нужен | ✓ |
| применение переноса (`confirmBooking`) | — | проверено при предложении | — | ✓ `confirmBooking.ts:122` |
| «Новая запись» студии (`createStudioBooking`, `studio/bookings.service.ts:45`) | админ студии | ✗ | ✗ | **✗** |
| перенос студии (`moveStudioBooking`) | админ студии | ✗ | — | ✓ `:350` |
| ручная запись мастера (`createSoloMasterBooking`, `lib/master/manual-booking.ts:17`) | мастер | ✗ намеренно (`:63-66`) | ✗ | **✗** |
| подтверждение модель-оффера (`api/model-applications/[applicationId]/confirm/route.ts`) | мастер назначил, клиент подтверждает | ✗ | ✗ | **✗** (`startAtUtc` из `offer.dateLocal` + `proposedTimeLocal`, `:205`, без сравнения с «сейчас») |

Интерфейс и сервер по min/max уже согласованы: пикер оператора всегда шлёт `?manual=1`
(`features/booking/components/operator-slot-picker.tsx:186`, в том числе при переносе), а
`listBookableSlots` в операторском окне режет только прошлое и не режет максимум
(`lib/schedule/bookable-window.ts:113-118`). Дальше горизонта расписания (92 дня) оператор не
уйдёт: `resolveMasterWorkWindow` берёт план дня из движка, а день за горизонтом закрыт.

Открытое — две вещи: (1) решение о min/max/новых клиентах на операторских путях нигде не записано
как ратифицированное (BACKLOG просит именно это); (2) **три пути создания принимают прошедшее
время** — по коду запрос мимо пикера (прямой POST) создаёт запись в прошлом. Оффер при этом можно
и создать на прошедшую дату: `api/master/model-offers/route.ts:482` пишет `dateLocal` без проверки.
Воспроизведение — юнит-тестом сервиса (первый шаг «Проверки»), живьём — через API.

## Что сделать

Предлагаемое правило (после ответа владельца, см. ниже): **окно клиента** — только там, где время
выбирает клиент; **оператор** (админ студии, мастер вручную) и **оффер** (время назначил мастер) —
без min/max/новых клиентов, но всегда «не в прошлом», в пределах горизонта и (у студии) рабочих часов.

1. `policy-enforcement.ts`: `assertNotInPast(startAtUtc, now, message)` → 409 `CONFLICT` (тот же код,
   что у двух существующих проверок). Перевести на неё `studio/bookings.service.ts:350` и
   `confirmBooking.ts:122` — одно правило вместо двух копий.
2. Вызвать её в `createStudioBooking` (до `resolveMasterWorkWindow`), `createSoloMasterBooking` и в
   подтверждении оффера сразу после вычисления `startAtUtc` (`route.ts:205`, текст «Время этого
   предложения уже прошло. Попросите мастера предложить новое.»). Создание оффера
   (`master/model-offers/route.ts`) — отказ на `dateLocal` раньше сегодняшней даты салона.
3. **Тип вместо сторожа (GUARD-INTEGRITY правило 8).** `createBookingRow` (`booking-row.ts:93`)
   получает обязательный `timePolicy: BookingTimeClearance` — брендированный объект
   `{ startAtUtc, kind: "client-window" | "operator" | "offer" }`, который выдают только
   `clearClientWindow(...)` (обёртка над `assertBookingWindow` + `assertAcceptsNewClient`; её
   результат кладёт в `BookingCoreContext` сам `resolveBookingCore`) и `clearOperatorTime(...)`
   (обёртка над `assertNotInPast`). Writer сверяет `timePolicy.startAtUtc` с `data.startAtUtc`
   (расхождение — 500, ошибка программиста). Восьмой путь создания без выбора политики времени не
   скомпилируется. Цена — одно поле в семи вызовах; переносы (`update`) типом не покрываются,
   там остаются явные вызовы из шагов 1–2.
4. Ратификацию записать в шапке `policy-enforcement.ts` таблицей «путь → политика» и в комментариях
   `manual-booking.ts:63` и `createStudioBooking` — чтобы следующий аудит не находил это заново.

## Решения владельца

1. **Действуют ли настройки окна мастера/студии на записи, которые создаёт и переносит админ
   студии?** (а) Нет — у админа прямая власть над календарём (инв. #22), минимум уже снят
   решением MANUAL-BOOKING-SLOTS-01. **Рекомендую.** Следствие: админ может записать дальше
   «максимума» мастера (но не дальше 92 дней) и к мастеру, закрытому для новых клиентов.
   (б) Да, полностью — пикер студии на клиентское окно; админ не сможет записать звонок «через
   час» при «минимум за 3 ч», что противоречит MANUAL-BOOKING-SLOTS-01. (в) Только максимум.
2. **Модель-оффер:** применять окно мастера к подтверждению? Рекомендую нет: время назначил сам
   мастер, а «новые клиенты» — и есть модели, ради которых оффер. «Не в прошлом» — да.
3. **Ручная запись задним числом** (занести уже прошедший визит ради CRM/выручки): сейчас сервер
   принимает, интерфейс не даёт. Рекомендую запретить (как у переноса). Если нужно разрешить —
   это отдельная форма и сразу статус `FINISHED`, а не `CONFIRMED` с напоминаниями.

## Готово, когда

- Таблица «путь → политика» ратифицирована и лежит в шапке `policy-enforcement.ts`.
- Три пути создания и две существующие проверки отказывают на прошедшее время одной функцией;
  оффер на прошедшую дату не создаётся.
- Вызов `createBookingRow` без `timePolicy` или с самодельным объектом — ошибка `typecheck`.

## Проверка

- Сначала — репродукция: сервисные тесты `createStudioBooking` / `createSoloMasterBooking` /
  подтверждения оффера с временем «вчера в рабочие часы» краснеют ДО фикса, после — 409 и ноль
  созданных строк (утверждать число вызовов writer'а, а не только код ответа — правило 10).
- Ратификация как тест: запись админа на окошко через 30 мин при «минимум за 3 ч» у мастера —
  проходит; то же через `resolveBookingCore` — `BOOKING_TOO_SOON`.
- `booking-row-time-policy.test.ts`: `@ts-expect-error` на вызове без поля и с литералом без
  бренда. `@probe`: сделать поле необязательным → директивы «неиспользованы», `typecheck` красный;
  обратная проба — вернуть, красного нет.
- Не должны сломаться: `availability-operator-window.test.ts`, `bookable-window-operator.test.ts`,
  `reschedule-enforcement.test.ts`, `policy-enforcement.test.ts`.
- Гейты: `typecheck`, `lint`, `check:encoding`, `check:mojibake`, `check:error-message-lang`.
- Живая: админ Vision (`+7 999 200 00 00`) — запись на ближайшее окошко и перенос; Анна
  (`+7 999 100 00 00`) — ручная запись; Елена (`+7 999 500 00 00`) — подтверждение оффера с

## Риски

- В проде могут быть офферы с прошедшей датой в статусе `APPROVED_WAITING_CLIENT` — после фикса их
  не подтвердить (так и должно быть); перед деплоем посчитать и, если есть, закрыть.
- Граница «сейчас»: окошко выбрано, отправлено через минуту — отказ. Так же ведёт себя перенос.
- Тип в `createBookingRow` трогает все семь путей создания — ревью по одному коммиту на путь не
  нужно, но прогон всех booking-тестов обязателен.
