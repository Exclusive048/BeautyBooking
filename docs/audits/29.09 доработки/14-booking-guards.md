**Источник:** `UPDATE-MANY-STATUS-WRITE`, `CONFLICT-SCOPE-PER-SITE` (BACKLOG); инв. #11, LOGIC-02 (контекст §5) · **Тип:** рефакторинг сторожей · **Объём:** M

## Что не так

**А. Запись статуса мимо `applyBookingTransition` (LOGIC-02).** Сторож `lib/bookings/transition.test.ts`
ищет регекспом `/booking\.update\(\{[\s\S]{0,400}?status:/` (`:177`) и сам называет слепые формы
(`:163-176`): `updateMany`, `upsert`, аргумент, собранный заранее, делегат в переменной. Перевод в
тип FIX-C6 измерил и отверг (зеркало дженериков Prisma) — решение в силе. Живого дефекта нет
(греп 2026-09-29): `booking.update(` — `transition.ts:68` и перенос студии `studio/bookings.service.ts:574`
(без статуса); `booking.updateMany` — **пять** мест: `reminders.ts:229`, `link-guest-bookings.ts:84`,
`studios/master-profile-split.ts:156, 164, 184` (три последних появились после записи в BACKLOG —
число растёт); статус не пишет ни одно. `upsert` — только сиды, `$executeRaw` с `UPDATE "Booking"` — нет.

**Б. Скоуп конфликта (инв. #11).** `lib/bookings/conflict-scope.test.ts`: семья — файлы с литералом
`notIn: ["REJECTED", "CANCELLED", "NO_SHOW"]` (`:199`), файл чист, если где-то в нём есть
`buildConflictScopeWhere(` (`:262`). FIX-C7 замерил: шестая копия парного скоупа проходит, если тот же
файл зовёт билдер в соседней функции. Сверх записи в BACKLOG найдено:
- **Семья по имени, а не по свойству** (GUARD-INTEGRITY правило 4): `lib/master/model-offers-mutations.ts:223`
  читает брони по окну пересечения со статусом через константу (`status: { in: ACTIVE_BOOKING_STATUSES }`) —
  в семью не входит вовсе. Сам сайт корректен (пикер, скоуп из `buildOccupancyBookingWhere`), но сторож
  о нём не знает.
- `studio/bookings.service.ts` — три чтения активных броней (`:189`, `:473`, `:525` — соседи по пакету,
  скоуп по клиенту законно без билдера) при двух вызовах билдера: файловая проверка это не выражает.
- Признак «арифметика пересечения» `OVERLAP_ARITHMETIC = "overlaps("` (`:211`) не видит инлайн-формы
  `start < itemEnd && end > itemStart` (`studio/bookings.service.ts:216, 503`).
- Проверка конфликта перед записью скопирована **пять раз** сверх `ensureNoConflicts`
  (`booking-core.ts:210`): предложение переноса `usecases.ts:70`, `confirmBooking.ts:167`, создание и
  перенос студии `:189`/`:473`, подтверждение оффера `model-applications/[applicationId]/confirm/route.ts:271`
  (своё окно `:256-257` вместо `buildConflictWindowWhere`); своя функция `overlaps` — в трёх файлах. В
  `confirmBooking.ts:144` набор профилей занятости читается `prisma` вне транзакции, хотя
  `resolveConflictOccupancyIds` требует того же клиента, что проверка.

## Что сделать

1. **Одна проверка конфликта.** `ensureNoConflicts(db, { …, excludeBookingId?, message? })` — исключение
   своей строки и текст отказа как параметры; пять копий перевести на неё (тексты 409 сохранить
   посайтово через `message`). Окно — только `buildConflictWindowWhere`, занятость — тем же клиентом
   (закрывает чтение вне транзакции в `confirmBooking`). Изоляцию по-прежнему ставит `bookingTransaction`
   (инв. #31, тип `BookingTx`).
2. **Общий AST-разборщик** `src/lib/testing/prisma-calls.ts` на `ts.createSourceFile` (прецедент —
   `scripts/check-include-where.mjs`, `lib/prisma-enums.test.ts`): находит вызовы `<любое>.booking.<метод>(арг)`;
   обращение `.booking`, которое не вызывается сразу (делегат в переменной, `tx["booking"]`), —
   «непроверяемый сайт»; идентификатор-аргумент разрешает до инициализатора в той же функции (с
   `?:` и скобками); читает ведущие комментарии инструкции для посайтовых отметок. Свои тесты на
   фикстурах: положительный и отрицательный вход, хвостовой комментарий (правила 2 и 6).
3. **Сторож статуса** (заменяет `STATUS_WRITE`): для `update | updateMany | upsert` (у `upsert` —
   `update` и `create`) `data`, разрешённая до литералов, с ключом `status` допустима только в
   `transition.ts`; неразрешимая `data` (параметр, вызов, спред неизвестного) и непроверяемый сайт —
   нарушение, если нет отметки `// booking-status-write-ok: <причина>` на самой инструкции.
   `reminders.ts:218-229` (`data` — `?:` из двух литералов) обязан разрешаться и проходить без отметки
   — это и есть контроль, на котором сгорел регексп.
4. **Скоуп по месту** (заменяет файловую проверку, `NON_CONFLICT_READERS`, `OVERLAP_ARITHMETIC` и
   жёсткий список пяти файлов): семья — чтение броней (`findMany | findFirst | findFirstOrThrow | count`),
   чей `where` содержит окно пересечения — спред `buildConflictWindowWhere(…)` либо пару
   `startAtUtc: { lt|lte }` + `endAtUtc: { gt|gte }`; статус в определение семьи не входит. Каждый такой
   сайт обязан в ТОМ ЖЕ `where` брать скоуп из `buildConflictScopeWhere(…)` или `buildOccupancyBookingWhere(…)`
   (напрямую или через константу из той же функции) либо нести `// conflict-scope-ok: <причина>`
   (соседи по пакету — `:525`, читающие поверхности из прежнего списка — по месту).
5. `docs/QUALITY-GATES.md`, GUARD-INTEGRITY правило 3: «исключения **и положительные проверки** —
   посайтовые» (правило 9 класс называет, правило 3 — всё ещё только про исключения).

Не нужны.

## Готово, когда

- Проверка пересечения перед записью брони — одна функция; копий и локальных `overlaps` нет.
- Оба сторожа работают по месту вызова; регекспы `STATUS_WRITE` и `ACTIVE_BOOKING_FILTER` удалены.
- В шапках сторожей — блоки `@probe` (A/B по одной оси) и явный список слепых форм.

## Проверка

- Пробы статуса (тот же файл `reminders.ts`, меняется одна ось): `status` в одну ветку `?:` → красный с
  именем сайта; то же через `const args = { where, data: { status } }; tx.booking.updateMany(args)` →
  красный; `const b = tx.booking; b.updateMany(…)` → красный (непроверяемый); исходный файл — зелёный.
- Пробы скоупа: в `studio/bookings.service.ts` (файл уже зовёт билдер) шестая копия с парным скоупом в
  соседней функции → красный (до правки — зелёный, FIX-C7); та же копия со статусом через константу →
  красный; снять отметку у соседей по пакету → красный; вернуть — зелёный.
- Тесты разборщика на фикстурах; все тесты `lib/bookings/`, `lib/studio/`, оффера; новый тест
  `ensureNoConflicts` с `excludeBookingId` (своя строка не конфликт, чужая — 409).
- Время: разбор ~1000 файлов — замерить `npm run test`; если прибавка > 10 с — кэш разбора на процесс.
- Гейты: `typecheck`, `lint`, `check:encoding`, `check:mojibake`.
- Живая (пункт 1 меняет рабочие пути): запись через виджет, запись админом Vision на занятое время
  (409 с прежним текстом), перенос с согласованием, подтверждение модель-оффера.

## Риски

- Консолидация трогает пять рабочих путей записи: регрессия превращается в двойную запись или ложный
  409. Держать поведенческие тесты каждого пути до и после; коммит консолидации — отдельно от сторожей.
- AST-сторож даёт ложный красный на новых законных формах — лечится отметкой на сайте, не на файле.
- Слепые формы остаются и называются: сырой SQL, делегат, полученный из функции другого модуля.
