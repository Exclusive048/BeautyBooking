# 28 · Часовые пояса: выбор только РФ, словарь меток не трогаем

**Источник:** `TZ-PICKER-RF-SPLIT` (BACKLOG, из RF-ONLY-SCOPE-01, флаг 4) · **Тип:** доработка + нужно решение · **Объём:** S
**Зависит от:** — (парная к 27: та закрывает автоматический канал не-РФ данных, эта — ручной)

## Что не так

Одни и те же списки сейчас служат двум целям: из них ВЫБИРАЮТ пояс и по ним ПОДПИСЫВАЮТ время.
- Словарь меток `TZ_CITY_RU` (`src/lib/ui/zone-label.ts:29-72`, блок «CIS» — `:58-72`: Алматы, Ташкент, Минск, Киев, Баку и др.) превращает пояс в подпись «(Алматы, GMT+5)». Его нужно оставить как есть: без него метка у живого провайдера на такой зоне деградирует до «(GMT+5)».
- Выбор пояса идёт через три списка:
  1. кабинет мастера — `CURATED_TIMEZONES` (`src/lib/ui/timezone-options.ts:20-39`): 12 зон РФ + «CIS» (`Asia/Almaty`, `Asia/Tashkent`, `Asia/Bishkek`, `Europe/Minsk`). Потребитель — `TimezoneSelector` (`src/features/master/components/profile/editable/timezone-selector.tsx:28`);
  2. и 3. админка городов — две **одинаковые копии** массива в `create-city-dialog.tsx:14-29` и `city-edit-form.tsx:41-56` (`src/features/admin-cabinet/cities/components/`): 13 зон РФ (с `Europe/Volgograd`, которого нет у мастера) + `Asia/Almaty`, сырые IANA-id без русских подписей.
- Тест прямо закрепляет старое поведение: «Almaty stays selectable» (`src/lib/ui/timezone-options.test.ts:14-15, 20`).
- **Выбор — не единственный вход.** Сервер принимает любую валидную IANA-зону: мастер — `src/lib/master/schemas.ts:61-67`, студия — `src/app/api/studios/[id]/route.ts:38-44` (в UI студии пояс только для чтения, но через API меняется), админка — `src/app/api/admin/cities/route.ts:46`, `[id]/route.ts:34-40`. Если убрать СНГ только из выпадающих списков, это закроет интерфейс, но не API.
- ⚠️ Не было в BACKLOG: форма правки города **не добавляет текущее значение** в список (`city-edit-form.tsx:152-162`). Город с поясом вне списка (например, `Asia/Novokuznetsk`) показывает в поле первый пункт, хотя в данных другое, а у мастера для этого уже есть `buildTimezoneOptions(current)` (`timezone-options.ts:49-55`).

## Что сделать

1. `timezone-options.ts`: разделить на
   - `RF_PICKER_TIMEZONES` — 12 зон, по одной на каждое смещение РФ (Калининград +2 … Камчатка +12), для кабинета;
   - `RF_ADMIN_TIMEZONES` — все зоны РФ из блока РФ `TZ_CITY_RU` (`zone-label.ts:30-56`, включая Волгоград, Саратов, Барнаул, Новокузнецк, Читу и др.), для городов — если так решит владелец (вопрос 2).
   `buildTimezoneOptions(current, list)` оставить: текущая зона вне списка по-прежнему добавляется первой — существующий провайдер на `Asia/Almaty` свою зону видит и не теряет.
2. Админка: обе формы берут список из `timezone-options.ts` через `buildTimezoneOptions(city.timezone, …)` — копии массивов удалить. Подписи те же, что у мастера («Москва (Europe/Moscow)»). Это же чинит показ зоны вне списка в форме правки.
3. Сервер (по ответу на вопрос 3): общий предикат `isSelectableTimeZone(next, current)` = `next ∈ список` **или** `next === current`. Применить при записи пояса мастера (`updateMasterProfile`, где известен текущий `Provider.timezone`), студии (`updateStudioProviderProfile`) и города в админке. Отказ — 422 `TIMEZONE_NOT_ALLOWED` со строкой из `UI_TEXT` («Выберите часовой пояс России»). Zod-проверку `isValidTimeZone` не снимать: она отсекает мусор, предикат — не-РФ зоны.
4. `zone-label.ts` и `TZ_CITY_RU` не трогать. Тест `zone-label.test.ts:53` («(Алматы, GMT+5)») остаётся зелёным: словарь меток не меняется.
5. `timezone-options.test.ts`: переписать закрепление. `Asia/Almaty` НЕ входит в списки выбора, но `buildTimezoneOptions("Asia/Almaty", …)` возвращает её первой с подписью «Алматы (Asia/Almaty)». Добавить сторож: каждая зона обоих списков лежит в блоке РФ словаря — новая зона СНГ в списке выбора валит тест.

## Решения владельца

1. **Разделяем выбор и словарь?** Да / нет. **Рекомендация: да.** Новый не-РФ пояс руками больше не завести, а старые данные подписываются по-прежнему. При «нет» пункт закрывается как «осознанно оставлено», вместе с флагом 4 RF-ONLY-SCOPE-01.
2. **Какой список у админки городов:** **А** — короткий, как у мастера (12); **Б** — полный список зон РФ (рекомендация: город — справочник, и точная зона, например `Europe/Volgograd` или `Asia/Novokuznetsk`, там уместна; мастеру же 27 пунктов с одинаковыми смещениями только мешают).
3. **Проверять на сервере** (шаг 3)? **Рекомендация: да.** Без этого разделение косметическое: пояс СНГ ставится одним запросом в обход интерфейса. Условие «или текущее значение» гарантирует, что сохранение других полей у провайдера на старой зоне не начнёт падать.
4. **Живые провайдеры и города на зонах СНГ:** оставляем как есть (подпись сохраняется, переводить не нужно)? Перед выкладкой — инвентарь:
```sql
SELECT timezone, count(*) FROM "Provider" GROUP BY 1 ORDER BY 2 DESC;
SELECT timezone, count(*) FROM "City" GROUP BY 1 ORDER BY 2 DESC;
```

## Готово, когда
- В кабинете мастера и в админке нельзя выбрать зону вне РФ; у существующих записей на такой зоне она видна и сохраняется.
- API не принимает новую не-РФ зону (при «да» на вопрос 3), но и не отказывает, если зона не менялась.
- Метки времени на зонах СНГ по-прежнему с городом.
- Копий списка зон в админке нет.
